## 2. Decimal 完全一致は**原文**で判定した

正規化 parquet は `mark_price` を `Float64` で保持している。**float を経由した
比較で Decimal 完全一致を判定してはならない**ため、本検証は**両側とも原文**から
Decimal を作った:

| 側 | 原文の出所 |
|---|---|
| candidate | `data/raw/binance/vision/mark_price_5m/BTCUSDT/*.zip` の CSV テキスト |
| REST | 公開 `GET /fapi/v1/fundingRate` の `markPrice` 文字列(メモリ上のみ) |

float 経路を外した根拠(実測): 2025-12 の markPriceKlines 8,928 行のうち
**4,897 行**で `repr(float(原文)) != 原文` である(`89766.10000000` → `89766.1`)。
末尾ゼロ自体は Decimal の**数値比較**では差にならないが、float 経由は
桁落ちを持ち込みうるので経路から外した。

テスト `test_a_difference_beyond_float_resolution_is_still_a_mismatch` が、
**float では区別できない差を不一致として検出する**ことを固定している。

### 2.1 「完全一致」は**数値**の一致であって文字列の一致ではない(誤読防止)

独立再計算で判明した内訳を明示しておく:

| 比較の仕方 | 一致件数 / 2,378 |
|---|---:|
| **Decimal(数値)一致** ← 本検証の判定 | **1,919** |
| 生文字列がバイト単位で同一 | **1,719** |

差の 200 件は `89766.10000000` と `89766.1` のような**表記の違いだけ**で、
数値としては等しい。**表記差を不一致とは数えていない。**
逆に言えば、本検証の「完全一致」は「同じ十進数値である」ことを意味し、
「同じ文字列を返している」ことまでは主張していない。

## 3. 検証1 — REST markPrice がある 2,378 決済

### 3.1 差の大きさ

| 指標 | min | p05 | p50 | p95 | p99 | max |
|---|---:|---:|---:|---:|---:|---:|
| 絶対価格差 (USDT) | 0 | 0 | **0** | 1.10638297 | 5.16184397 | **13.97680496** |
| 絶対 bps 差 | 0 | 0 | **0** | 0.16811 | 0.66757 | **2.39797** |
| 符号付き bps 差 | **−1.72176** | −0.04031 | **0** | 0.01450 | 0.46064 | **+2.39797** |

(nearest-rank。中央値が 0 なのは 80.7% が完全一致だからである。)

**符号付きの量では `min` / `p01` / `p05` も必ず出す。** 上側だけを載せると
負の裾(−1.72 bps)が成果物から見えず、分布が片側であるかのように読める。
不一致 459 件の符号は両側にある(candidate > REST と candidate < REST の双方)。

### 3.2 timestamp の対応

規則は `floor_5m(funding_time)`。決済時刻がバー先頭から何 ms 内側かの分布
(2,378 件):

```text
0ms:1711  1ms:313  2ms:82  3ms:57  4ms:50  5ms:48  6ms:29  7ms:25  8ms:18
9ms:14  10ms:13  11ms:4  12ms:2  13ms:4  14ms:2  15ms:3  16ms:3
```

この 2,378 件の subset ではジッタの最大は **16ms**、
**全 6,576 決済まで広げると最大 47ms** である(どちらも実測)。
いずれにせよ5分バー(300,000ms)に対して桁違いに小さく、
「どのバーに属するか」は曖昧にならない
(実データで 6,576 決済 → 6,576 本の相異なるバー。多対一は 0 件)。

### 3.3 mark_samples / 状態 / layer

| 項目 | 値 |
|---|---|
| `mark_samples` 分布 | **300 が 2,377 件**、298 が 1 件 |
| mark 経路の状態 | **`observed` が 2,378 件**(利用不能な状態は 0) |
| layer 内訳 | layer 1 `literature_in_sample` 1,736 / layer 2 `contaminated_confirmation` 642 |

**mark バーの欠測・曖昧対応は 0 件**である(だから `incomplete_conformance` には
ならず、`proxy_only` になった)。

### 3.4 不一致 459 件の性質(**説明であって救済ではない**)

- 年別: 2023 = 45 / 2024 = 273 / 2025 = 141
  (不一致**率**は 2023 = 24.3% / 2024 = 24.9% / 2025 = 12.9%)
- 決済時刻別: 00:00 = 141 / 08:00 = 157 / 16:00 = 161(**偏りが無い**)
- バー先頭からの ms: 0ms が 370 件。**ジッタが 0 の決済でも不一致になる**。
  しかも**不一致率は offset 0 の方が高い**(370/1,711 = 21.6% に対し、
  offset > 0 は 89/667 = 13.3%)。したがって
  **「ms のジッタでバーを取り違えている」という説明は向きが逆であり成り立たない**
- **459 件のうち 428 件は REST の値がそのバーの `[low, high]` の内側**にあるが、
  **31 件は範囲の外**である。すなわち決済時 mark は
  **そのバーで観測された値ですらない**ことがある
- バー内の値幅(high − low)の中央値は、一致した 1,919 件で 123.49、
  不一致 459 件で 126.89 と**ほぼ同じ**。したがって
  **「荒れたバーだから外れる」という説明は成り立たない**

### 3.5 なぜ一致しないのか(**独立検証が突き止めた機序**)

不一致の原因は**バー選択規則の誤りではなく、粒度の不一致**である。

1. **markPriceKlines は 1Hz の離散サンプルの要約である。**
   `mark_samples = 300 / 5min` すなわち毎秒1本。バー N の `close` は第299秒、
   バー N+1 の `open` は第300秒(= 境界)のサンプルである。
2. **その帰結として、`open == 直前バーの close` は全バーの 29.9% しか成り立たない。**
   境界に「1秒ぶんの隙間」が常にある。
3. **459 件の差は、実測した「mark の1秒あたり変動」の分布に完全に収まる**
   (超過は 0 / 459)。すなわち **1 サンプル分の位相ずれ**で説明できる大きさである。
4. 459 件の内訳: **190 件は直前バーの `mark_close` と桁まで一致**、
   169 件は直前バーの `close` と当バーの `open` の**あいだ**、
   100 件はその外だが 2 バーの範囲内。
   **範囲外の 31 件は 31/31 が直前バーの `[low, high]` の内側**である
   (= 「バーが始まる前の mark」)。
5. **どの 5m OHLC フィールドを組み合わせても 100% には届かない。**
   `open` と直前バー `close` の OR をとっても 2,109 / 2,378 = **88.7%** が上限。
6. 一致するかどうかを分けているのは**バー内の変動幅ではなく、値の刻み**である。
   0.1 tick に貼り付いた値は 99.5% 一致するのに対し、指数由来の 8 桁フル精度値は
   64.9% しか一致しない(一致した 1,919 件と不一致 459 件でバーの値幅の中央値は
   123.49 と 126.89 でほぼ同じ = **「荒れたバーだから外れる」ではない**)。

> **含意**: 決済時 markPrice と 5分 markPriceKlines は、**近いが同一の系列点ではない**。
> funding の markPrice は**連続的に計算された mark を決済時刻ちょうどでスナップ
> ショットした値**であり、5分バーの `open` は**1Hz サンプルの最初の1点**である。
> **両者を一致させる規則は存在しない**(規則を精緻化しても直らない種類のずれである)。

## 5. 判定規則(事前に固定)

```text
比較対象が 0 件                          → not_verifiable_no_overlap   (最優先)
対応不能または曖昧が 1 件でもある        → incomplete_conformance
1 件でも不一致                           → proxy_only_not_exact_reconstruction
すべて Decimal 完全一致                  → candidate_deterministic_reconstruction
```

実測は **不一致 459 / 対応不能 0 / 曖昧 0 / 比較対象 2,378** なので
**`proxy_only_not_exact_reconstruction`** である。

**`not_verifiable_no_overlap` は事前登録の3判定に無い第4の帰結**であり、
敵対的検証で見つかった欠陥への対応として追加した。3判定は「比較できた標本がある」
ことを暗黙の前提にしており、標本 0 件に当てはめると「全件一致」が**空虚に真**になって
`candidate_deterministic_reconstruction` が出てしまう。
**「検証できなかった」を「決定的に再構成できた」に化けさせない**ための分岐である
(今回の実測はこの枝を通っていない)。

### 5.1 敵対的検証で直した実装上の欠陥(**いずれも今回の数値は変わらない**)

| # | 欠陥 | 対応 |
|---|---|---|
| 1 | 比較対象 0 件で `deterministic` になりうる | 第4判定 `not_verifiable_no_overlap` を追加 |
| 2 | 多対一の検出が **REST markPrice を持つ決済だけ**で行われ、片方に REST が無い衝突を見逃す | 占有の計数を**全決済**に変更 |
| 3 | REST 応答の出所(SHA-256 / 要求範囲 / 取得時刻)を破棄しており、一致件数を後から再検証できない | `rest_page_provenance` として artifact に記録(7 ページ) |
| 4 | 封印の適用が「canonical parquet がたまたま 2025-12 で終わっている」ことに依存 | 決済の読み出しに**明示的な cutoff** を追加 |
| 5 | mark gap probe の参照が cwd 相対で、見つからないと**無言で** `route_unverified` へ縮退 | repo 起点の絶対パスにし、**無ければ停止**する |

## 8. 既知の未解決事項(**本検証の外にあるが、隠さない**)

`data/normalized/binance/mark_price_BTCUSDT_5m.parquet` の実ファイル sha256 は、
版管理されている2つの manifest
(`binance_mark_price_mark_price_BTCUSDT_5m.json` と `phase8_inputs_v1.json`)の
記録と**一致していない**(行数 628,978・列・ts 範囲・欠測数はいずれも一致)。

- 原因は本作業ではなく、**環境ごとに parquet のバイト列が変わる**ことである。
  同じ raw zip から再生成しても sha256 と size は一致しない。
- **本検証の結論はこのずれの影響を受けない。** probe は parquet ではなく
  **raw zip の CSV 原文**を読んでいる(§2)。
- 同種のずれは `metrics` / `premium_index` / `binance_features` にも
  **本作業より前(2026-08-17)から**存在する。
- 「環境依存の parquet hash だけで既存 manifest を更新しない」という方針に従い、
  **manifest を書き換えていない。** 環境非依存の指紋(公開 zip の SHA-256 から作る
  `source_digest`)は `phase8_inputs_v1.json` の記録と**完全に一致**しており、
  「どの一次データを読んだか」はそちらで固定されている。
- **どう解消するかは設計判断**であり、本検証では決めていない。
