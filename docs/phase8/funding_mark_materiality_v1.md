**`mark_open` は exact ではない**(1,919 / 2,378 = **80.70%** 一致、**459 件不一致**)。
**その事実は変わらないまま**、誤差の大きさは funding 収支の水準に対して極めて小さい。

**2,378 決済ぶんの累積絶対誤差**:

| 量 | 累積 \|誤差\| | 符号付き純額(相殺後) |
|---|---:|---:|
| 価格 (USDT) | 477.59875084 | +23.75279814 |

> **2,378 決済ぶんの「1 BTC あたり単位誤差」の絶対値を足し合わせると 0.047 USDT、
> 名目換算では 7.04e-7(= 0.00007%)である。**
>
> **これは建玉を仮定した量ではない。** 各決済について
> 「exact な mark で計算した場合との差」を 1 BTC あたりで出し、
> **決済をまたいで算術的に足しただけ**である。実際にその全 2,378 決済で
> 建玉していたことを想定していないし、数量も保有期間もコストも入っていない。
> 対象期間は 2023-10-31T08:00Z 〜 2025-12-31T16:00Z(**792 日 ≒ 2年2か月**)。
>
> **これは「proxy が exact である」ことを意味しない。** 一致率は 80.70% であって
> 100% ではない。ここで言えるのは**誤差の大きさ**だけである。
>
> **符号付きの純額が絶対値合計より小さいことを「相殺されるから無視してよい」と
> 読んではならない。** 相殺は標本の性質であって、機序の性質ではない。
> 判定には**絶対値**の側を使う。

## 1. 誤差の定義(**結果を見る前に固定した**)

```text
price_error   = mark_open − rest_mark                      [USDT]
bps_error     = (mark_open / rest_mark − 1) × 10,000       [bps]
cashflow_diff = (mark_open − rest_mark) × funding_rate     [USDT / BTC / 決済]
notional_ret  = funding_rate × (mark_open / rest_mark − 1) [無次元]
```

`cashflow_diff` は §8.1 の `q · MarkPrice(s) · f(s)` を **`q = 1 BTC`** で評価した
ときの差である(`q` を掛ける前の単位誤差)。**戦略の損益ではない。**

### 1.1 比較は3入力すべて原文の Decimal で行う

| 入力 | 原文の出所 |
|---|---|
| `mark_open` | `data/raw/binance/vision/mark_price_5m/BTCUSDT/*.zip` の CSV テキスト |
| `rest_mark` | 公開 `GET /fapi/v1/fundingRate` の `markPrice` 文字列 |
| `funding_rate` | `data/raw/binance/vision/funding_rate/BTCUSDT/*.zip` の CSV テキスト |

**正規化 parquet(Float64)を数値の経路に入れない。** `funding_rate` は誤差に
掛かる係数なので、ここも原文で扱う。

### 1.2 層別も結果を見る前に固定した

- **年**: 決済時刻の UTC 年
- **volatility 帯**: そのバー自身の `(mark_high − mark_low) / mark_open` を bps にし、
  **10 / 25 / 50 / 100 bps の固定境界**で5帯に切る。**分位点で切らない**
  (分位で切ると帯の定義が結果に依存する)
- **funding rate の符号**: `positive` / `negative` / `zero`

`mark_high` / `mark_low` は**帯の計算にしか使わない**。primary 候補ではない。

### 1.3 分位点の方式

```text
nearest-rank: 昇順に並べて index = ceil(q × n) − 1。**線形補間ではない。**
```

**方式を書かないと再現できない。** 線形補間を既定にする再現者は別の数字を出す。
符号付きの量では `min` / `p01` / `p05` も必ず併記する(上側だけだと負の裾が見えない)。

## 2. 母集団と再確認

| 項目 | 件数 |
|---|---:|
| 比較した決済(REST markPrice があり、mark 経路が利用可能) | **2,378** |
| **Decimal 完全一致** | **1,919(80.70%)** |
| **不一致** | **459(19.30%)** |
| 比較から外した決済(primary が利用不能) | **0** |

**この「0」は 2,378 件の内側の話である。** REST mark が無い layer 1 の 4,198 決済は
そもそも比較母集団に入らないので、この台帳には現れない
(それらの可用性は[再構成 probe](funding_mark_reconstruction_probe_v1.md) §4 が数えている)。

**再確認できた。** [再構成 probe](funding_mark_reconstruction_probe_v1.md) の
1,919 / 459 と一致する。

- **一致率を 100% へ丸めていない。**
- **459 件を「許容差内の一致」へ分類し直していない。** 誤差の**大きさ**を測っただけである。
- **`open` と直前バー `close` の OR(2,109 件)を primary の成績として使っていない。**
  本分析の母集団は固定 primary(`mark_open`)のみである。
- primary が利用不能な決済の誤差を **0 として集計に混ぜていない**(該当 0 件)。

## 5. この分析が**言っていないこと**

1. **proxy が exact だとは言っていない。** 一致率は 80.70% である。
2. **459 件を「許容差内」と分類し直していない。** 分類は再構成 probe のまま
   `proxy_only_not_exact_reconstruction` である。
3. **strategy の損益を計算していない。** `cashflow_diff` は
   「同じ1決済を exact な mark で計算した場合との差」であって PnL ではない。
   建玉・数量・保有期間・コスト・清算を一切考えていない。
4. **昇格や GO の判断をしていない。** ここにあるのは入力誤差の大きさだけである。
5. **相殺を根拠にしていない。** 符号付き純額は併記したが、判定には絶対値を使う。
6. **layer 1 の 4,198 決済については何も言えない**(REST mark が無く比較できない)。
   ここで測ったのは **layer 1 のうち 1,736 件**と **layer 2 の 642 件**である。
